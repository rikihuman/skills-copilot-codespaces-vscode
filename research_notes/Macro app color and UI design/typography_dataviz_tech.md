## Typography: typefaces, tabular figures, numeral hierarchy, Dynamic Type, licensing

### Takeaway
Use the system fonts (SF Pro / SF Pro Rounded on iOS, Roboto / Roboto Flex on Android) for body text and Dynamic Type. If you want a brand typeface, choose an OFL font with true tabular figures (Inter v4 or Manrope), and turn tabular figures on for every changing or compared number: calorie counters, macro grams, weight values, table columns. Check that the build you ship actually includes the `tnum` feature, because the Google Fonts build of Inter has had OpenType features removed.

### Cited Findings
- Tabular figures all have the same width, so columns of numbers line up and values don't shift sideways as they change. Proportional figures are the default in many UI fonts. — [DEV: tabular numbers in CSS](https://dev.to/alanwest/tabular-numbers-in-css-font-variant-numeric-vs-monospace-hacks-25cn); [Preuss Type: tnum feature](https://preusstype.com/techdata/otf_tnum.php)
- Inter's default numerals are proportional lining figures. Tabular and oldstyle variants are available through OpenType features (`tnum`). — [Lexington Themes: Inter stylistic sets/OpenType](https://lexingtonthemes-com.pages.dev/blog/inter-stylistic-sets-css-tailwind)
- CoinGecko's brand guide, for a numbers-heavy product, "highly recommend[s] the use of tabular numbers (tnum) within the Inter V4 typeface for scanning and uniform column widths." — [CoinGecko brand typography](https://brand.coingecko.com/visual-identity/typography/primary-typeface)
- Blender's UI adopted Inter with features ss01, ss02 and tnum, which shows the tabular-Inter pattern in a dense numeric UI. — [Blender PR #112795](https://projects.blender.org/blender/blender/pulls/112795)
- GNOME/Adwaita proposed enabling tabular figures by default across all UI elements so numbers don't jump. — [GNOME GTK issue #41](https://gitlab.gnome.org/GNOME/gtk/issues/41)
- Guidance on when to use each: tabular figures where users compare numbers (timers, metrics, tables), proportional figures in running text. — [bjrn.vercel.app: tabular nums usage](https://bjrn.vercel.app/blog/tabular-nums-usage-and-comparison)
- iOS: an article explains how SF Pro's numerals behave and how to request monospaced digits in iOS UI. — [Seyfeddin: Tabular numbers in iOS](https://seyfeddin.synaps.media/writing/tabular-numbers-in-ios/)
- Flutter exposes `FontFeature.tabularFigures()` for tabular digits in Text styles. — [Flutter API: FontFeature.tabularFigures](https://api.flutter.dev/flutter/dart-ui/FontFeature/FontFeature.tabularFigures.html)
- Segoe UI is inconsistent: some weights default to tabular figures and others to proportional. Don't assume a font's default. — [blog.yuo.be: Segoe UI tabular figures](https://blog.yuo.be/2024/07/20/segoe-ui-tabular-figures-and-directwrite/)
- Inter and Manrope are both licensed under the SIL Open Font License and available on Google Fonts. — [MadeGoodDesigns: Manrope vs Inter](https://madegooddesigns.com/manrope-vs-inter/); [WebDesignerDepot: Manrope](https://webdesignerdepot.com/free-download-manrope-font-family)
- The Inter files distributed by Google Fonts "do not include many of Inter's font features," which were removed to reduce file size. Get Inter from rsms/inter (GitHub) if you need `tnum` and the stylistic sets. — [Inter (typeface) wiki mirror](https://wiki.krisyotam.com/content/wikipedia_en_all_nopic_2026-03/Inter_(typeface)); [Inter v3 site](https://d.rsms.me/inter-website/v3)
- Manrope lists Tabular Figures among its OpenType features (secondary source). — [terrapkg Manrope package](https://github.com/terrapkg/pkg-manrope-fonts)
- Apple system families are SF Pro and SF Pro Rounded (iOS/iPadOS/macOS/tvOS), with SF Mono for monospaced text. Text styles rescale with Dynamic Type, so the reference sizes are not fixed values (secondary summary of the HIG through iOS 26). — [Axiom typography reference](https://charleswiltgen.github.io/Axiom/reference/typography-ref)
- Apple uses SF Pro Rounded in Fitness rings, Apple Watch complications and some Health screens (secondary blog). — [Blake Crosley: SF Pro typography system](https://blakecrosley.com/blog/sf-pro-typography-system)
- Liquid Glass (WWDC25, iOS 26) is Apple's new translucent material. Guidance is to use system components so they adopt it automatically. — [SuperDesign: Apple design system](https://www.superdesign.dev/blog/apple-design-system)

### Inferences
- Recommended stack: system UI font for chrome and body text, so Dynamic Type, Liquid Glass legibility tuning and localization come free. Then either (a) the system font with monospaced digits (SwiftUI `.monospacedDigit()`, Compose `fontFeatureSettings = "tnum"`) for all live numbers, or (b) a bundled OFL brand font (Inter v4 from rsms/inter, or Manrope) for numerals and headings only. SF Pro Rounded is the most "Apple Health-native" choice for big hero numbers on iOS, but Apple's license limits SF fonts to Apple platforms, so Android needs a counterpart (for example Inter or Manrope). Including SF on Android is not allowed.
- Numeral hierarchy for a macro app: (1) a single hero number per screen (calories remaining or trend weight), at roughly 2 to 3 times body size, semibold, tabular; (2) macro grams at title size with units in a smaller, lighter weight ("142 g" with the "g" de-emphasized); (3) secondary deltas and targets at caption size, using color plus a sign/arrow (never color alone). Scale all of these with Dynamic Type / font scale, and test at the largest accessibility sizes, where hero numbers may need to wrap or truncate units.
- Pick a font with clearly distinct 1/l/7 and 0/O (Inter's ss01/ss02 alternates address this). Decimal weights such as 81.4 kg need an unambiguous decimal point.
- DM Sans: no license or tabular-figure details were confirmed in this research (see Gaps).

## Data visualization for nutrition/fitness

### Takeaway
Weight: plot raw weigh-ins as faint dots or a pale line under a bold smoothed trend line (EMA or similar), and use a non-zero y-axis for line charts, which is acceptable. Macros: prefer aligned bars or progress bars against targets over donuts, and use donuts or pies only for simple part-to-whole shares. Avoid multi-segment stacked bars for comparing non-adjacent segments. Calorie bars must start at zero, with the target drawn as a rule or band. Make every chart accessible with VoiceOver audio graphs (Swift Charts does most of this automatically) and with text summaries.

### Cited Findings
**Trend-weight charts (industry patterns)**
- MacroFactor shows raw scale weight as a pale line and its algorithmic Weight Trend as a deep purple line. The latest trend value is shown as "Current Trend." Because the trend looks backward, it sits below scale weight during gaining and above it during losing. — [MacroFactor help: Weight Trend](https://help.macrofactorapp.com/dashboard/weight_trend/)
- Happy Scale offers four smoothing methods: Exponential Smoothing, a seven-day moving average, Happy Scale Smoothing (recommended) and double exponential smoothing. It presents the trend to "show the underlying trend... rather than the day-to-day noise," and gives a moving-average mode for users demotivated by flat daily scale numbers. — [Happy Scale support](https://happyscale.com/support); [App Store listing](https://apps.apple.com/us/app/happy-scale/id532430574)
- Another app ("True Weight," Municorn) uses a blue trend line over a grey scale-weight line, the same pattern. — [Municorn help](https://intercom.help/municorn-limited-9e71b379f21d/en/articles/13375649-what-s-the-difference-between-scale-weight-and-true-trend-weight)
- The exponentially smoothed moving-average trend line comes from John Walker's *The Hacker's Diet*. — [fourmilab Hacker's Diet](https://fourmilab.ch/hackdiet/www/subsubsection1_2_4_0_4_4.html)

**Macro distribution: perception evidence**
- Cleveland & McGill-style results: aligned bars are clearly better than pies, and stacked bars do worse, especially when comparing segments that are not adjacent or not on a common baseline. — [EagerEyes: Stacked bars are the worst](https://eagereyes.org/blog/2016/stacked-bars-are-the-worst); [Tableau Research: Four Experiments on the Perception of Bar Charts](https://www.tableau.com/nl-nl/research/publications/four-experiments-perception-bar-charts)
- Simkin & Hastie found pie charts as accurate as bar charts and better than stacked bars for proportion judgments. Heer & Bostock found pies beat length encodings but not position encodings. Spence & Lewandowsky suggest pies are better for judging summed sectors and simple shares (25%, 50%). — [EuroVis 2019 short paper (diglib.eg.org)](https://diglib.eg.org/bitstream/handle/10.2312/evs20191162/007-011.pdf); [arXiv 2508.01881](https://arxiv.org/html/2508.01881v1)
- NN/g-specific guidance on pies vs bars was not found in this search (see Gaps).

**Axes and baselines**
- Correll, Bertini & Franconeri (CHI 2020, "Truncating the Y-Axis: Threat or Menace?"): truncated bar charts exaggerate perceived effect sizes, and the effect persists even when viewers are told about the truncation. Line charts encode by position, so they need not include zero. — [arXiv 1907.02035](https://ar5iv.arxiv.org/html/1907.02035); [NSF PAR PDF](https://par.nsf.gov/servlets/purl/10196700)
- Observable: "never OK to crop the y-axis... except when it is." Context-dependent guidance for line charts. — [Observable blog](https://observablehq.com/blog/never-okay-crop-y-axis-except-when-it-is)

**Chart accessibility**
- Apple Audio Graphs: a view adopts `AXChart` and exposes an `accessibilityChartDescriptor` (`AXChartDescriptor` with title, axes, data series, summary). `AXLiveAudioGraph` covers live data. Users reach audio graphs through the VoiceOver rotor, and each data point plays a pitch. — [Apple: Representing chart data as an audio graph](https://developer.apple.com/documentation/accessibility/representing-chart-data-as-an-audio-graph.md); [Apple: Audio graphs](https://developer.apple.com/documentation/accessibility/audio-graphs.md); [WWDC21 10122](https://developer.apple.com/fr/videos/play/wwdc2021/10122/)
- Swift Charts builds the accessibility tree and audio graph automatically from chart data. Custom (non-Swift-Charts) charts must supply their own `AXChartDescriptor`. Audio graphs cannot be tested in the Simulator. — [Create with Swift: accessible Swift Charts](https://createwithswift.com/making-charts-accessible-with-swift-charts); [Swift with Majid: Audio graphs](https://swiftwithmajid.com/2021/09/29/audio-graphs-in-swiftui/); [Kodeco tutorial](https://www.kodeco.com:443/31561694-ios-accessibility-in-swiftui-create-accessible-charts-using-audio-graphs)
- In the React Native world, a third-party `react-native-ax-chart` package bridges AXChartDescriptor. — [react-native-ax-chart README](https://cdn.jsdelivr.net/npm/react-native-ax-chart@0.3.0/README.md)

### Inferences
- **Weight chart spec:** scale weigh-ins as small low-contrast dots, with no line connecting them, because a connecting line exaggerates noise. Draw the trend as a 2 to 3 pt saturated line. The y-axis may be non-zero but should use padded "nice" bounds, and the tightest default range should not make a 0.2 kg change look dramatic: set a minimum y-span, such as 2 kg or 4 lb. Optionally draw the goal weight as a dashed rule and the projection as a dashed continuation. Label the current trend value directly at the line end instead of using a legend. Offer 1W/1M/3M/6M/1Y/All presets (Happy Scale's customizable shortcuts are a precedent).
- **Macros:** for "today vs target," use three horizontal progress bars (P/C/F) on a common baseline with the target marked. These are position/length encodings and the most accurate. A small donut or ring is fine as an at-a-glance hero for the calorie budget or macro split, since that is a simple part-to-whole judgment, but always pair it with numeric labels. Avoid stacked 100% bars for weekly macro comparisons; use small multiples (one bar chart per macro) instead.
- **Weekly calories:** use zero-based bars with a horizontal target rule or a shaded tolerance band (for example ±5 to 10%). Color bars by in/over status with a secondary cue (pattern or icon), not color alone. Show weekly average as text.
- **Accessibility parity on Android:** Compose has no audio-graph equivalent, so provide `contentDescription`/semantics summaries ("7-day average 2,140 kcal, target 2,200") and a "View as table" toggle on both platforms. A non-native stack (MAUI/Flutter/RN canvas charts) loses Swift Charts' automatic audio graphs unless you bridge AXChartDescriptor yourself.

## Iconography, illustration, motion and haptics

### Takeaway
Use body-neutral, diverse or abstract illustration (or no bodies at all) and frame progress in function or trend terms. Don't use before/after photos or isolated body parts in onboarding, marketing or achievements. Pair logging feedback with system haptics (success/selection), keep it subtle, and respect Reduce Motion.

### Cited Findings
- A 2025 *Sociology Compass* study of 95 weight-loss apps' App Store descriptions found two stigma mechanisms: a lack of body diversity in app imagery, and moralization of body weight (fatness framed as personal failure). — [UIC repository](https://repositori.uic.es/handle/20.500.12328/5107); [UPF repository](https://repositori.upf.edu/items/2bd6cc69-00c8-4130-ae2e-d10b66a2b80b/full)
- A study of obesity-related apps on Apple's App Store had raters assess screenshots and artwork. It flagged stigmatizing imagery such as isolated body parts and stereotypes, and recommended avoiding content that creates stigma or unhealthy expectations. — [IOS Press SHTI230447](https://ebooks.iospress.nl/pdf/doi/10.3233/SHTI230447)
- Weight Watchers dropped before/after photos. Critics argue such images make people near the "before" feel undesirable. A counterpoint is that some users find transformation photos motivating. — [The Star: before and after photographs](https://www.thestar.co.uk/read-this/how-before-and-after-photographs-promote-unattainable-body-ideals-49092); [Parachute Media](https://theparachutemedia.squarespace.com/beauty/problem-with-weight-loss-transformation-pics)
- A body-neutral fitness app concept used neutral tones, avatars instead of photos of a "correct" body type, and capability-focused framing. — [UvA Masters of Media](https://mastersofmedia.hum.uva.nl/2019/10/you-cannot-weigh-beauty-but-your-body-can-be-commercialized)
- Apple HIG "Playing haptics": standard controls (switches, sliders, pickers) play system haptics automatically. Use feedback generators for the predefined notification (success/warning/error), impact and selection patterns. Haptics are physically felt and can interfere with other experiences, so use them judiciously. — [Apple HIG: Playing haptics](https://developer.apple.com/design/human-interface-guidelines/playing-haptics.md); [Apple Core Haptics](https://developer.apple.com/documentation/corehaptics.md)
- A cross-platform RN haptics library (Software Mansion "Pulsar") collects haptics design reading. — [Pulsar: Good to read](https://docs.swmansion.com/pulsar/articles/good-to-read/)

### Inferences
- Icon style: use SF Symbols on iOS (they scale with Dynamic Type and support hierarchical/palette rendering) and Material Symbols on Android (variable weight/fill/grade). For a single cross-platform set, use an outline icon set with 2 px strokes and rounded joins, and keep food icons neutral (no "good/bad food" red/green moral color coding).
- Illustration: abstract shapes, food and kitchen scenes, plates and charts rather than bodies. If people appear, show diverse body sizes, ages, skin tones and abilities, mid-activity. Avoid scales-as-hero imagery and tape measures around waists.
- Language and visuals for coaching: "trend," "adherence," "energy," not "cheat," "guilt" or "bad day." Show over-target days neutrally (for example amber, not red alarm).
- Micro-interactions: a light selection haptic for each macro stepper tick, and a success notification haptic plus a brief ring-fill animation on completed log or check-in. Avoid celebratory haptics for weight loss specifically, since that moralizes weight. Honor Reduce Motion (cross-fade instead of spring) and allow haptics to be turned off.

### Gaps
- No Android/Material haptics design guidance was retrieved (Material has "haptics" guidance, but it did not appear in search results).
- No 2025–2026 survey of health-app illustration trends was found. The recommendations above are inferred from stigma research plus platform conventions.
- No outcome or usability data was found comparing body-neutral vs conventional imagery.

## Design-system implementation: .NET MAUI vs Avalonia/Uno vs Flutter vs React Native vs native

### Takeaway
For a solo senior .NET engineer, .NET MAUI 10 (LTS, Nov 2025) is viable for the core app: C# offline-first sync with SQLite/EF Core, MVVM, LiveCharts2 or free Syncfusion/DevExpress charts, and Shiny.Health for HealthKit and Health Connect. However, home-screen widgets (WidgetKit/Glance), Live Activities and native chart accessibility (Swift Charts audio graphs) still require native Swift/Kotlin code. Flutter and React Native have larger health/chart ecosystems. Native SwiftUI+Compose gives the best chart accessibility, widget and Liquid Glass/Material 3 Expressive fidelity, at the cost of two codebases. A pragmatic split: MAUI app plus thin native widget extensions, or a shared .NET core library with native UIs if chart and widget quality is the product's differentiator.

### Inferences
- **Decision matrix for this app (numbers- and chart-heavy, widgets, health data, offline-first):**
  - *.NET MAUI 10:* reuse of C#, EF Core/SQLite and sync logic (for example CommunityToolkit.Datasync or a custom sync layer) is the biggest win for this developer. Charts: LiveCharts2 (MIT, fully custom-drawable, good for trend-weight scatter-plus-line) or the Syncfusion open-source toolkit. Health: Shiny.Health. Weaknesses: widgets and Live Activities need native extensions; Skia-drawn charts get no automatic VoiceOver audio graphs (you would bridge `AXChartDescriptor` through a platform handler); Liquid Glass and M3 Expressive fidelity lags native; and MAUI's 6-month per-version support means yearly upgrades.
  - *Uno / Avalonia:* consistent Skia pixel rendering is attractive for a strongly branded chart UI, but mobile screen-reader support on Uno's Skia renderer was still "in progress" as of Aug 2026. That is a material accessibility risk for a health app.
  - *Flutter:* best "single design system on both platforms" story (one widget tree, `FontFeature.tabularFigures`, fl_chart or Syncfusion Flutter charts, health plugins). It requires learning Dart, and widgets are still native.
  - *React Native/Expo:* largest ecosystem of health libraries, and native views give better accessibility. It requires JS/TS.
  - *Native SwiftUI + Compose:* Swift Charts (automatic audio graphs, Dynamic Type), WidgetKit/Glance, Liquid Glass and M3 Expressive at full fidelity, with no bridging. Cost: two UIs. A shared .NET backend and sync API still let the .NET skills carry over to the server.
- Recommended token approach regardless of stack: keep color, type, spacing and radius tokens in Figma Variables with Light/Dark modes, export to DTCG JSON, and use Style Dictionary with custom formats to emit (a) a MAUI `ResourceDictionary` XAML plus C# constants, (b) Swift/Kotlin tokens for the widget extensions, so widgets and the app share one palette. Use `AppThemeBinding` (MAUI) or semantic token aliases for light/dark. Keep chart series colors as semantic tokens (`chart.trend`, `chart.scale-dot`, `macro.protein/carb/fat`, `target.band`).
- Tooling: Apple Design Resources (iOS 26 Figma/Sketch kits including Liquid Glass) and the Material 3 Design Kit plus Material Theme Builder for Android parity. Figma Community health/fitness UI kits can serve as inspiration, but none was specifically verified.
